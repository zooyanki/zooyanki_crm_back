# ADR 0003. Мультиарендность и RLS с самого начала

Дата: 2026-09-11. Статус: принято.

## Контекст

Сейчас система обслуживает один аккаунт Авито, принадлежащий владельцу.
В перспективе — несколько клиентских аккаунтов, возможно нескольких
арендаторов.

## Решение

`tenant_id` добавляется в каждую доменную таблицу с первой миграции,
доступ ограничивается политиками Postgres Row-Level Security. Авторизация
на площадках абстрагирована через `channel_accounts.auth_type`, который
уже сейчас различает `client_credentials` и `authorization_code`, хотя
используется пока только первый.

## Обоснование

Добавить `tenant_id` в пустую схему стоит почти ничего. Добавить его
в схему с боевыми данными — это миграция каждой таблицы, ревизия каждого
запроса и высокий риск утечки данных между арендаторами из-за забытого
условия. RLS дополнительно страхует от таких забытых условий на уровне БД.

## Последствия

- Каждый запрос выполняется в транзакции с установленным
  `SET LOCAL app.tenant_id`, это делает `PrismaService`.
- Появление клиентских аккаунтов потребует реализовать OAuth-коллбэк
  `authorization_code`, но не миграцию данных.
- Небольшой overhead на политики RLS. Приемлемо.
